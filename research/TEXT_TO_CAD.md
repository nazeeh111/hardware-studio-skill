# Text-to-CAD routes for Hardware Studio

23 October 2026. This compares public source with this Mac's existing OpenCascade generator. Source inspection is distinguished from local execution. No third-party model or CAD repository was installed or executed during this comparison.

## What transfers

The inspected [generation pipeline](https://github.com/3mindsales/text-to-cad/blob/0d76f91daef501f187311022452f69bf79c29469/src/texttocad/pipeline/generate.py) normalizes the model's parameters before construction and returns no solid after its repair budget is exhausted. Its [correction implementation](https://github.com/3mindsales/text-to-cad/blob/0d76f91daef501f187311022452f69bf79c29469/src/texttocad/pipeline/correct.py) rebuilds from a parameter patch and retains the caller's previous specification on failure. These support the design choice to keep an editable specification as the source of truth. No code was copied.

Its [geometry validation](https://github.com/3mindsales/text-to-cad/blob/0d76f91daef501f187311022452f69bf79c29469/src/texttocad/geometry/validate.py) checks solid count, B-rep validity, volume and envelope. Its thin-wall warning uses the smallest overall bounding-box dimension. That is not a measurement of every local wall thickness. Hardware Studio should keep semantic requirements, dimensions, local clearances, readback integrity and physical fabrication as distinct checks.

A process timeout and Python syntax filter do not, by themselves, establish filesystem or network isolation for generated code. Hardware Studio's new text route accepts parameter JSON only and does not execute model-authored programs. More general geometry needs a separate, demonstrated execution boundary and meaningful shape/feature tests before exposure through a browser.

## Original implementation

`tray-intent.js` proposes changes to the current supported tray spec using a selected installed Ollama model. It rejects unsupported response fields, malformed geometry, unresolved required information and unchanged proposals. The complete proposed spec and model assumptions are visible before acceptance. Acceptance refuses a proposal if the form changed since generation. Cancel, timeout, rejection and discard retain the form. The local CAD service still builds and checks actual geometry only after a separate generation action.

This is text editing of a constrained tray model. It does not establish arbitrary text-to-CAD, correct interpretation of every instruction, automatic feature preservation, maker-part fit, strength, tolerances or fabrication readiness. Public Pages cannot reach the local CAD route; text edits are enabled only on a loopback-hosted workbench with Ollama available.

## Local trial

The [retained trial package](../examples/text-edited-tray/README.md) records the actual prompt, installed model digest, one rejected free-form JSON response, accepted schema-constrained parameters and fresh-process CAD readback. The resulting 120 × 80 × 25 mm tray had one solid and matching STEP/STL spans. This verifies one simple local edit through browser export and the CAD generator, without a general model-quality claim.


## Extending geometry without executing model programs

On 23 October, a further review compared the current bounded primitive route with the official [CadQuery topology/API explanation](https://cadquery.readthedocs.io/en/latest/primer.html) and [build123d introductory examples](https://build123d.readthedocs.io/en/latest/introductory_examples.html). CadQuery documents its OpenCascade boundary representation and higher-level interfaces. The build123d examples demonstrate sketch extrusion, point-list profiles, selectors, fillets and chamfers. Those are stronger authoring routes for broader CAD than adding every feature manually to a custom wrapper; neither library was installed or benchmarked here.

For the immediate missing capability, the installed OCP binding already supports a polygon wire, planar face and prism. Hardware Studio now accepts a bounded simple polygon as data, with matching JS/Python checks, explicit local axes, winding normalization, and topology rejection. The static builder extrudes it and retains the existing connected-solid, material-effect, region-check and fresh-process readback gates. This extends custom straight-edged outlines without introducing model-authored executable code or a new shared runtime dependency. It does not add arbitrary sketch interpretation, curved profiles, fillets, constraints, lofts or assemblies. Reassess a maintained higher-level CAD library when those operations become the next demonstrated requirement.


## Further review: assemblies and model evaluation

The official [build123d assembly guide](https://build123d.readthedocs.io/en/stable/assemblies.html) represents assemblies as labeled part trees with local placements and accumulated global locations. This is a useful future route for editable multi-part geometry. Hardware Studio's current mounting arrows record intent only: they have no joint constraints, local coordinate frames or solved placements. Adding better connected project plans does not create a CAD assembly solver. No build123d installation or execution was performed.

The May 2026 [Text2CAD-Bench paper abstract](https://arxiv.org/abs/2605.18430v1) describes 600 human-curated cases across four complexity levels and reports weaker performance on advanced geometry. This supports separating simple local successes from general capability claims. Hardware Studio has not run that benchmark. A future comparison should retain prompts, expected features and dimensions, failed attempts, execution success and geometry checks; one visually plausible render is insufficient evidence.

The Text2CAD authors' newer [DreamCAD project](https://sadilkhan.github.io/dreamcad2026/) describes multimodal generation through parametric surfaces and downstream topology recovery. These are author-reported capabilities; no weights, runtime or Mac compatibility were tested here. Freeform surfaces and solid topology recovery are a materially different requirement from the current constrained feature sequence. They do not resolve component selection, power topology, mounting dimensions or build instructions automatically.

For the present product gap, the original local drafting boundary now carries tools, assumptions, mounting relationships, linked steps and proposed power-rail bindings together. It accepts bounded JSON rather than generated code and clears current ratings and verification claims. This improves the editable concept record. It is not an implementation or evaluation of those research models.


## Existing-project changes as explicit edits

Hardware Studio's original `project-change.js` applies a bounded list of record additions, replacements and removals against original IDs/indexes. It retains unmentioned records and CAD, makes automatic evidence/current/check resets visible, and rejects unsupported fields or dangling references. The browser compares the captured workspace and CAD bytes again before saving. This is a coordinated project-record revision route; it does not edit a solid or solve an assembly. The [retained trials](../examples/project-revision/README.md) separate actual model output, deterministic replay, storage/history behavior and untested hardware claims. This addresses a different failure mode from CAD execution: a whole-record regeneration can lose manually checked work even when the resulting JSON is structurally valid. No external code or research model was installed for this addition.

One concrete next capability is an **exportable inspection sheet from the actual loaded STL**, with labeled top/front/right views, consistent scale and the mesh's identity. It can use the existing viewer without installing a second CAD kernel or training a model. A retained request and optional local vision observations could accompany it later. Exact dimensions, solid count, material probes and STEP readback must remain separate deterministic evidence. A model's favorable visual opinion must not set project verification flags. Missing views and unavailable vision should be reported explicitly; neither should silently count as completed inspection. The three-view export has now been implemented in the original viewer. The [retained browser export](../examples/profile-plate/inspection/inspection.png) and [manifest](../examples/profile-plate/inspection/inspection.json) were checked against the retained STL and projected pixel extents. Two-mesh browser exports were identical before/after display lift and zoom changes; hiding the cover excluded it from output. The loopback viewer now also offers optional local vision observations on that exact captured image. It accepts request-owned qualitative feature IDs, validates bounded visible/not-visible/unclear output and retains model prose separately from all deterministic checks. Model errors, cancellation and rejected output are NOT RUN; earlier completed artifacts are retained. The [Ollama generate API](https://docs.ollama.com/api/generate) documents base64 image input and structured JSON output, while [show-model metadata](https://docs.ollama.com/api-reference/show-model-details) identifies vision support. The app checks local model capability and digest before/after generation; no cloud model or model-authored code is used. The [completed and canceled browser trials](../examples/vision-observation/README.md) retain exact input/output artifacts and a documented imprecise model description. They establish a narrow workflow result, not an accuracy benchmark. This supplies inspection evidence, without a tested improvement in model accuracy.

The current official [build123d 0.13.0 joint documentation](https://build123d.readthedocs.io/en/stable/joints.html) also clarifies a future assembly boundary: `connect_to()` repositions a part once and does not maintain a live binding. Labeled placements and joint ranges would improve authoring, but they do not by themselves establish a general constraint solver, collision freedom or measured physical fit. This narrows the earlier assembly recommendation; it does not add a dependency to the present product.

## First-part generation: deeper implementation findings

23 October 2026. A fresh GitHub API tree read confirmed the same pinned revisions for textcad, CADAM and Text2CAD listed above. This pass inspected their actual generation boundaries, rather than adding another repository list. No repository was installed, model downloaded, upstream code copied or cloud AI called.

**First-part creation needs different context from editing.** textcad's [`generate_scad`](https://github.com/dbhavery/textcad/blob/1163dfddcaba6fa003d9106f49ac1c0d66aa013c/textcad/codegen.py) has distinct fresh, compiler-repair and visual-repair branches. Fresh generation receives the requested description; repair branches receive prior code and failure feedback without repeating that description. Its system prompt also supplies example dimensions and asks for realistic dimensions. This is a useful implementation caution: a plausible artifact can inherit invented numbers or lose original requirements during repair. Hardware Studio should capture the original brief, chosen target part, explicit millimeter constraints and instruction together; create mode should not include an unrelated example or previous part. Essential missing dimensions should produce a visible needs-input result, while unsupported operations should remain unsupported. These are recommendations from source inspection, not demonstrated model behavior.

**Keep difficult geometry mechanics in trusted construction code.** The same textcad file prepends a through-hole helper and asks the model to select the axis and position. This reduces the generated decisions needed for hole orientation and cutter length. Hardware Studio can apply that principle through its existing static builder and validated feature JSON. A source-valid cylinder still does not prove a requested through-hole: check actual bore location, axis, material removal and dimensions after STEP readback. Do not infer correctness from a model-authored probe that merely agrees with its own wrong coordinates.

**A successful visual loop has a narrower meaning than dimensional validation.** CADAM's [`aiChat.ts`](https://github.com/Adam-CAD/CADAM/blob/e339e3ad85601bb1e23a5ff9c7f33b51ddf602f5/src/server/aiChat.ts) requests repeated model construction followed by a browser-produced seven-view sheet. Its [`build_parametric_model` contract](https://github.com/Adam-CAD/CADAM/blob/e339e3ad85601bb1e23a5ff9c7f33b51ddf602f5/shared/chatAi.ts) returns compile success and optional view/image metadata; that contract has no measured tolerance, bore or fit verdict. Its [worker](https://github.com/Adam-CAD/CADAM/blob/e339e3ad85601bb1e23a5ff9c7f33b51ddf602f5/src/worker/openSCAD.ts) executes browser OpenSCAD and returns mesh output and compiler logs. These inspected boundaries support a future bounded repair loop, with retained attempts and deterministic failures supplied separately from qualitative observations. They do not establish fabrication readiness. A first-part route should initially retain a reviewable proposal before a separate CAD build, preserving the last valid source when generation, validation or saving fails.

**Text2CAD is not a direct millimeter-preserving replacement.** Its [`macro.py`](https://github.com/SadilKhan/Text2CAD/blob/669a81472ede2269837c22a4d00070eaac360c82/CadSeqProc/utility/macro.py) sets an eight-bit representation. [`CADSequence.normalize()`](https://github.com/SadilKhan/Text2CAD/blob/669a81472ede2269837c22a4d00070eaac360c82/CadSeqProc/cad_sequence.py#L565-L595) rescales global geometry and explicitly documents that global normalization as non-reversible; local sketch normalization is separately reversible. The [user-input path](https://github.com/SadilKhan/Text2CAD/blob/669a81472ede2269837c22a4d00070eaac360c82/Cad_VLM/test_user_input.py) reconstructs predicted vectors into STEP without supplying a retained original-unit scale. A usable integration would need an explicit unit/scale adapter and independent requested-feature checks. This is source evidence about the pipeline, not a measured numerical error or a claim that all dimensional prompts fail.

The next acceptance case should therefore start from an empty CAD source and a named project part, generate a fully dimensioned simple part unrelated to the shipped examples, independently check its bounds and openings, and retain request/model identity alongside the proposed source. Missing dimensions, unsupported geometry, changed request/model/target/project, cancellation, reload and export need explicit outcomes. Naming the target in that record does not yet bind a CAD asset to a bill-of-materials part or supply assembly placement, joints or collisions. Those remain a separate product requirement.
