# Hardware Studio

Turn the requested device into an engineering work package whose claims can be checked. Start from the function, environment, dimensions, power source, budget and fabrication access. Ask for a missing constraint only when it changes the architecture; proceed with explicit assumptions otherwise.
When a brief is incomplete, gather the few missing conditions that change architecture or acceptance. Record supplied answers as user constraints and keep unanswered questions explicit. Do not invent ratings, dimensions or environmental limits to make a design look complete. The companion browser app can add deterministic follow-up questions to a brief before a local model drafts it; those questions do not establish any physical specification.

If given a sketch or photo, record what is visibly present and what the user wants it to mean. A visual reference can guide layout and appearance, but scale, hidden parts, material, part numbers, pinouts and electrical ratings require separate evidence. Keep the image with the editable project when the user wants that reference preserved. The browser app's **Draw sketch** supports editable strokes and labels with undo/redo; choose **Use sketch**, then create a project to retain it beyond the tab. Pending references and unfinished drafts use tab session storage when available. Saved sketches can be edited from Overview and export both a JPEG and `reference-sketch.json`. Preserve that source when revising a drawing. Only the JPEG goes to the selected local vision model; user labels are annotations, not independently verified specifications.

Build a connected design record: requirements, chosen architecture, exact parts with quantities and source dates, interfaces and pin-level connections, power and thermal budgets, mechanical dimensions and clearances, assembly and bring-up steps, test criteria, cost estimate, and unresolved risks. Keep IDs consistent across artifacts. Give unknowns a visible status at the point where they matter. For each power rail, record the supply rating and each assigned part's peak current per unit, then calculate demand using quantity and compare headroom with an explicit target. Leave unknown currents blank; a partial worksheet cannot pass a whole-device power review.
For a build plan, list required tools and prerequisites separately from steps. Link each step to the part IDs it actually touches, describe an observable acceptance check, and keep unselected or unverified equipment as an assumption. Reconcile step links when a part changes; the browser editor and skill checker can detect missing part IDs but cannot establish that a step is electrically or mechanically safe.

Verify decisive properties against original manufacturer datasheets and current supplier listings. Record the specific document URL and check date for each part marked verified; supplier listings serve a different purpose from specifications. Check voltage ranges, pin functions, logic levels, peak and continuous current, connector and cable ratings, orientation, dimensions and mounting patterns. Calculate margins rather than relying on a generated diagram. A search result, marketing render or approximate price does not validate a component.
When an exact part is selected, record the pin names from that revision's maker document and link each conductor to named endpoints. For physically unlabeled connector positions or carrier-board bus rails, use an unmistakable `ASSIGNED` prefix in the project inventory and state that these are proposed assembly labels, not maker pin names or exact hole addresses. Check that the count of assigned positions does not exceed the connector's actual openings and that no position is assigned two conductors. Use the app's pin-inventory cross-check to catch inconsistent labels, then separately verify voltage domains, direction, common ground, conductor/contact current, voltage drop and physical retention. A matching string is not a validated electrical connection.
Export `connections.csv` from the app or its project ZIP for a line-by-line review. Its state column reports missing references or endpoints, inventory mismatches, and `ASSIGNED` labels still needing a physical port or hole map; a row may describe several conductors. Split those rows into individual, verified conductors before treating the record as a schematic or build wiring list.

Use a schematic tool or other suitable format for actual electrical documentation. For geometry that must fit or be manufactured, make an editable dimensioned model and verify clearances. Use a conceptual illustration only to explain arrangement, labeled as such. Select local CAD or Blender by the artifact the user needs; neither is mandatory for a text-only design question. Physical energizing, fabrication and purchasing require the user's separate authority and a design review proportionate to the hazard.

For a worked package, the [Pico + NeoPixel tray example](https://github.com/nazeeh111/hardware-studio-skill/tree/main/examples/pico-neopixel-tray) retains parametric source, STEP readback, manufacturer-model fit checks, negative collision cases, a separately rendered Blender view and a source-backed provisional electrical path. Its power worksheet deliberately stays incomplete while supply and auxiliary current data are unknown. It is an example of the evidence chain, not a certified or fabrication-ready device.

For a rectangular prototype tray, use the repository's [parametric tray generator](https://github.com/nazeeh111/hardware-studio-skill/tree/main/tools/tray-generator) when its wall, boss, locator/hole and edge-cutout schema fits the request. Write the millimeter spec from measured or manufacturer dimensions, run `generate.py`, and inspect `verification.json` plus the dimensioned SVG. Keep the spec and CAD files with the project. The generator verifies modeled shape and file readback; run separate exact-part fit, clearance, connector and physical checks before any readiness claim.
When maker STEP models exist, `tools/tray-generator/fit.py` compares explicitly placed models with a generated tray and each other. Use a manifest with measured source-model orientation and placement, inspect collision volumes and envelope margins, and keep the report alongside source hashes. A nominal no-intersection result is not physical fit or fabrication approval.

When a user wants to set tray geometry in the browser, the app's Assembly view opens a [tray workbench](https://nazeeh111.github.io/hardware-studio-skill/tray.html). It previews dimensions and exports the same JSON input consumed by the local generator. Its optional lift-off cover is a separate plate with an outside skirt and nominal side gap; it can also cut a measured rectangular light opening while leaving a minimum plate web beside the tray walls. Check opening placement, cable access, retention, ventilation and intended visible output. An open hole is not a diffuser or proof of optical performance. The app keeps a valid tray spec in project JSON and as `tray-spec.json` in the project ZIP. The project ZIP and preview do not contain generated STEP/STL or prove physical fit.
To generate STEP/STL from the browser on this Mac, run `sh tools/tray-generator/run-local.sh --port 4174` from the repository root, then open its loopback URL. The launcher selects an OCP-enabled Python interpreter. The local server supplies a readback-checked CAD ZIP with separate lid files when selected; the public Pages origin cannot invoke it. The same fit checker compares supplied STEP models with tray and seated lid and reports each collision separately. The generated package still needs exact-part fit, functional enclosure and fabrication review.

For text edits to an existing tray spec, use **Describe the change** in the local workbench with a selected installed Ollama model. Supply explicit dimensions for new features, inspect every proposed parameter and assumption, and apply only after review. A form change invalidates the proposal. The subsequent CAD action builds geometry through the existing generator; the model never supplies executable code through this route. This supports constrained tray edits, not arbitrary CAD or automatic interpretation guarantees.

For a connected part beyond the tray schema, the repository's [feature solid modeler](https://nazeeh111.github.io/hardware-studio-skill/solid.html) supports ordered box/cylinder additions and cuts and simple polygon extrusions, with explicit axis, origin and millimeter dimensions. Use it only when those primitives represent the requested part. Keep the feature JSON as the editable master and the generated STEP as geometry; the applied feature JSON is retained as optional `solidSpec` in project JSON, history and ZIP (`solid-spec.json`), while checked STEP/STL is downloaded separately from the modeler. Open it from the project’s Assembly tab to bind source to that project; the direct modeler URL retains a separate standalone draft. New projects open without source; examples load only on explicit request. Supply selected material/void probes for important openings or retained regions, inspect operation volume changes and fresh-process readback, and compare decisive dimensions or volume against independent expectations. A text proposal passing input rules has not yet passed the geometry checks. The [generator guide](https://github.com/nazeeh111/hardware-studio-skill/tree/main/tools/solid-generator) defines limits; the worked bracket demonstrates analytical volume and a missing-hole negative case. Use the dimension controls for feature sizes, positions and polygon points; the expandable JSON editor retains the same editable source. Polygon profiles take 3–64 simple straight-edged corners with an implicit closing edge; +Z uses local X/Y, +X uses Y/Z, +Y uses Z/X. Reject crossings, touches, repeated or collinear corners. A profile may be used as a selected region check too. The worked profile plate compares analytic volume and fresh-process readback. Curved or multiply connected sketches, fillets, threads, lofts and assemblies need a suitable broader CAD workflow.

For a first part, choose **Create a new part** in the local solid modeler, select its target project part and provide explicit dimensions, hole locations and interfaces. It sends the captured brief and target context without inheriting current/example geometry. Use **Edit current part** to preserve a supplied source. Review ready sources and their assumptions; needs-input or unsupported responses apply nothing. The prompt asks for missing dimensions, but model recognition is not guaranteed. Compare important numeric intent against independently measured exported bounds, hole locations and volume. Changed instruction, mode, model, target, project or saved source blocks acceptance; a checked save precedes source replacement. Download the proposal ZIP before reloading to retain request, model digest and raw response. A selected target is context only: projects retain one shared solid source, without per-part CAD attachment or solved placement. Failed or canceled retries preserve the earlier completed proposal download.

For interactive mesh inspection, open the repository's `cad-viewer.html`. It reads up to four local STL files or the worked tray/cover example, with orbit, zoom, top/front views and visibility controls. STL has no unit metadata: confirm that the coordinates represent millimeters before trusting displayed dimensions or GLB scale. Its GLB exporter converts millimeters to meters, preserves original positions and excludes the example's display-only cover lift. Use the STEP fit checker for collision evidence; viewing meshes does not calculate physical clearance. For a retained visual comparison, download the viewer’s three-view inspection ZIP. Confirm its visible-mesh list, original positions, assumed units, common pixel scale and geometry hashes. The hash identifies parsed Float32 render geometry, not original STL bytes. The PNG excludes hidden meshes and the display-only cover lift. It is not a dimensioned drawing; no AI inspection is run. Keep model opinions separate from deterministic geometry checks and project review marks. When a qualitative comparison would help, the loopback viewer can ask an installed local vision model to observe the captured top/front/right image against 1–8 feature lines. Use the retained observation ZIP to inspect its image hash, geometry hashes, captured request, model digest and raw text. Treat every visible/not-visible/unclear result as unverified model prose, including favorable observations. The feature cannot measure dimensions or verify physical properties, and changes no project marks or CAD. Common measurement and physical-property terms reject as a conservative intake aid, without a guarantee that every phrasing is recognized. Read NOT RUN as unavailable, canceled, timed out or rejected output. A changed request or viewer marks an older capture; canceled retries retain the previous completed observation separately.

For a tray currently edited in the local workbench, choose **Generate and inspect in 3D**. It freezes a validated spec in the tab's session storage, then the viewer calls the local CAD service and checks generated STL hashes, triangle counts and dimensions against fresh-process readback. The snapshot expires after 30 minutes; returning to the workbench and opening a new preview captures new dimensions. The viewer's CAD ZIP action regenerates from that frozen spec. Confirm its title and dimensions before downloading. The public static site cannot run this generation route.
On the same local page, choose up to four maker STEP files and explicitly place each model to run a nominal solid-intersection check. Download the report with model hashes, overlaps, distances and cavity margins. Use the CLI manifest when a rotation outside the browser presets is required. Files remain local and temporary; no-intersection is not physical-fit approval.

If a browser save reports a changed workspace, download that tab's attempted-workspace backup before reloading; reconcile projects from the backup rather than retrying a stale save. For unreadable or changed tray drafts, retain the original-byte download and export the current spec before replacing saved geometry. These controls detect stale reads and do not supply collaborative editing.

Deliver the editable sources and a plain-language build and test guide. Separate verified, estimated, inferred and untested items. If a constraint or source cannot be checked, make the next required check concrete instead of calling the design ready to build.

When the user wants an interactive project, produce a Hardware Studio JSON file using [the project format](references/project-format.md). Validate its structural links with `node scripts/check-project.mjs /absolute/path/to/project.json` from this skill folder, then direct the user to import the file in the [Hardware Studio app](https://github.com/nazeeh111/hardware-studio-skill). That checker verifies data shape and cross-references; it does not validate electrical or mechanical engineering.
If the JSON includes a tray spec, the checker also applies the app's tray input rules. Passing those rules means the requested shape can be submitted to the generator, not that any real component fits.

For the public product pattern that inspired this workflow, read [Blueprint observations](references/blueprint-observations.md) only when comparing features or interpreting that website. It is not an API or an engineering standard.


When using the browser's local AI concept draft, inspect its captured request and all proposed relationships before acceptance. New drafts include tools, assumptions, mounting intent, part-linked build/test steps and proposed rail bindings. All supply/load currents remain unknown, prices and evidence links are cleared, and review/completion marks stay false. This is an editable concept, not checked engineering. Use **Download draft JSON** to retain a proposal independently. If the intake changes during generation, acceptance is blocked; generate again from the newer request or reconcile the downloaded proposal manually. Brief text and answers persist in tab storage; unreadable saved request bytes require a backup before explicit replacement. AI discovery and generation are limited to the local app; public Pages does not probe Ollama.


For a revision to an existing Hardware Studio project, preserve the requested baseline and unmentioned records instead of regenerating the whole plan. The local app's **Revise with local AI** proposes bounded edits to parts, connections, mounts, rails, linked steps, tools and assumptions. Inspect all before/after records, including automatic resets of evidence, current values and completion. An identity change clears that part's price, pins and specification marks; quantity-only changes retain per-unit part evidence. Wire edits conservatively invalidate affected load-current evidence, while unchanged supply hardware ratings and unrelated branch currents stay recorded. Model text remains unverified, including claims of completed testing. CAD, images and evidence links are preserved by this route; revise geometry separately in the appropriate workbench.

Retain **Download revision ZIP** before applying when a portable change record is needed. It includes `before-project.json`, `proposed-project.json` and `change-record.json` with the exact model patch and derived resets. Apply only while the captured project, workspace and CAD sidecars still match; a changed request or model also blocks the old proposal. Reopen from the latest project after a conflict, and reconcile the saved proposal deliberately. The app refuses to apply if its recovery snapshot cannot be saved in History. Existing notes are preserved and the captured request plus a deterministic record of edit operations are appended; raw model prose remains in the downloadable patch, never in the added provenance; overflowing the notes limit rejects the change. Use manual editing when the bounded vocabulary or context cannot express the required revision. A structural gate or successful replay does not establish hardware behavior.
